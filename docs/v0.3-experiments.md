# V0.3 — causal predictive scheduling experiment

Run with Node.js 18+:
```sh
node test-v3.mjs
node test-v3.mjs --full > results-v3.json
```

## Model changes
- Separate fixed migration overhead (2 ticks in the benchmark) from context-switch overhead (0/1/3 ticks). Both consume simulated CPU time and delay queued jobs.
- Commit a dispatched job to at least one useful CPU tick after a nonzero switch cost. Policy switches cannot interrupt committed dispatch or migration. Periodic MLFQ boosts can be skipped at these boundaries; this is a modeling choice, not Linux behavior.
- Snapshot version 3 includes migration accounting and dispatch lock; V0.2 snapshots are not compatible.
- Predictive controller compares 48-tick shadow projections every 48 ticks, using observed completed CPU bursts and current service age. No true remaining burst lengths, future arrivals, future I/O durations or wake times are consumed by the predictor. Forecast considers only ready/running jobs and approximates each with a single estimated remaining CPU burst. It omits future arrivals/wakes, prediction runtime cost, and cache effects. It is not AI/LLM generation.
- The default policy switches if estimated reduction in integrated queue-wait loss (extra weight for not-yet-served jobs) exceeds max(3, 8% of current predicted loss). This forecast objective differs from final equal-weight normalized mean response/turnaround score; weights, horizons, cost and threshold are illustrative engineering choices.

## Results
Rerun directly from fetched committed source in a JavaScript runtime: 3 targeted fixtures and 840 complete runs (120 paired groups x 7 policies), no assertion failures. Seeds 101–108 are disjoint from V0.2 (1–12), with changed workload distributions and five families. This is a synthetic evaluation, not an independent external test corpus.

| Policy | Mean score (RR=1, lower better) | Strict wins vs per-group best static |
|---|---:|---:|
| FCFS | 3.0358 | 0 |
| RR | 1.0000 | 0 |
| MLFQ | 0.8744 | 0 |
| V0.2 heuristic under V0.3 model | 1.3283 | 0 |
| Predictive | 1.1563 | 31 |
| No relative margin (absolute floor remains) | 1.0527 | 34 |
| Ignore migration cost in forecast (actual cost still charged) | 1.1856 | 31 |

Predictive strict wins by family (24 each): CPU 14, IO 1, mixed 2, phase 3, sparse 11. By switch cost (40 each): 0 -> 0; 1 -> 11; 3 -> 20. Mean relative regret vs per-group best static: CPU -0.11%, IO +15.32%, mixed +53.15%, phase +96.57%, sparse +28.09%. Mean regret is the mean of paired ratios, not ratio of aggregate means. Margin variant improved 40 and worsened 58 groups versus no relative margin. Forecast migration accounting improved 31 and worsened 41 groups versus ignoring it; average score was lower with accounting. Neither ablation gives universal dominance; no causal claim about all workloads or inferential significance.

## Interpretation and next steps
Do not promote this controller as production default. MLFQ is best by mean score among tested policies. Predictive wins concentrate at positive synthetic switch costs; phase shifts are particularly poor. Possible mechanisms: missing arrivals/wakes in forecast, inaccurate residual-service estimates, objective mismatch, and evaluation interval. These are hypotheses, not demonstrated root causes. The normalized score can amplify cases with very small RR response times (denominator floor = 1 tick). Compare absolute metrics and fixed service-level objectives before optimization. Next: causal replay with logging, ablate wake/arrival prediction and objective alignment, calibrate on separate training workloads, freeze and validate on a new heldout set. No Linux, QEMU, eBPF, UI or real latency validation yet.
